# Ironlog

A personal hypertrophy and strength tracker for one lifter. It is used on a phone at the gym. It ships two ways from one source file: as a Claude artifact (a hosted single-page app with cloud sync) and as a standalone installable web app (dist/, hosted on GitHub Pages, offline, data on the phone). Since r24 every pull request is also published as a separate preview app at /preview/ (dist-preview/), to try on a phone before merging. Build r46, state schema v5.

## What is in this repo

- `src/`: the source since r36, in 24 parts cut at the code's section headers (01 to 03 the page head, styles and markup; 10 to 29 the script, from start-up through storage, sync, accounts, 15 analytics, 16 the load engine, 17 adjusting the next sets, the screens, sheets, actions and events; 99 the close). `npm run join` writes them in name order into `index.html`. Edit `src/`, never `index.html` by hand: `tests/r36.js` fails when the two differ. The parts are pieces of one page and one script in one function scope, not modules.
- `index.html`: the whole app, joined from `src/` and committed, because the Claude artifact, `scripts/build.js` and every test use this one file. About 10,700 lines: CSS, markup, then one script in an IIFE. No framework. Chart.js 4.4.1 and SortableJS 1.15.2 load from cdnjs, with jsdelivr as fallback, and the fonts come from Google Fonts. three.js 0.159 (the 3D body) is imported as a module from jsdelivr or unpkg, only when the 3D view opens; the standalone build ships its own copy in `vendor/`.
- `tests/`: Playwright suites that drive the real page in Chromium. `tests/h.js` is the harness. It serves Chart.js, Sortable and the fonts from `node_modules`, blocks every other network call, and can fake the clock (`clock`), seed localStorage (`state`), and inject a mock cloud (`setup`).
- `scripts/build.js`: writes the standalone app to `dist/` (fonts and libraries copied in, manifest, icons, service worker); `--preview` writes the preview build to `dist-preview/`. `scripts/icons.py` draws the icons into `assets/`, and the preview's (the same mark over a striped band) into `assets/preview/`.
- `supabase/functions/delete-account/index.ts`: the server function behind Delete my account (pasted into the Supabase dashboard). `supabase/functions/feedback-to-issue/index.ts`: turns each feedback report into an issue in the private tickets repository (`FEEDBACK.md`). `.github/workflows/keepalive.yml`: a daily ping so the free project never pauses. `.github/workflows/publish.yml`: `npm test` on every pull request and push to `main`; a passing push to `main` publishes `dist/` to `gh-pages`.
- `scripts/cloud-supabase.js` and `supabase.config.json`: accounts and cloud sync for the standalone app. The build copies the script into dist/ as `cloud.js` with the supabase-js bundle, and injects the project URL and publishable key (both public; row level security protects the data). The secret key never goes in this repo. `SUPABASE.md` is the dashboard setup.
- `baselines/r11.html` to `r29.html`, and `r29-5.html` (r29.5), `r30.html`, `r30-2.html` (r30.2), `r31.html`, `r31-1.html` (r31.1), `r31-2.html` (r31.2) and `r31-3.html` (r31.3), `r32.html`, `r32-1.html` (r32.1), `r34.html`, `r34-1.html` (r34.1), `r34-2.html` (r34.2), `r35.html`, `r36.html`, `r37.html`, `r38.html`, `r39.html`, `r40.html`, `r41.html`, `r42.html`, `r43.html`, `r44.html` and `r45.html`: previous published builds. `tests/migration.js` saves data with them and loads it into the current build. Never delete them. When you publish a new build, add the build it replaces here.

## Invariants (never break these; each was a ruling or a bug)

Collected in r44 from the code map below, so they are read first. The map says where each lives.

- **Data:** never lose or overwrite what the lifter typed: loads, reps, targets, settings (`refreshBlock`, `syncDraftPlan`, `rowBlank`, `appBand`). A saved set never has an empty load. What is stored is always RIR, and every set stores the number exactly as typed. A migration only adds; it never overwrites a value the user set. New optional fields stay absent when unset, so record hashes and sync are unchanged.
- **Sync across builds:** settings keys keep one order across builds (`secOrder` added last); records keep unknown fields in the order they came (`keepExtra`); a new field is relied on only once every device runs a build that keeps it ("update every device"). Never write anything in `normalize` that depends on the device (it also runs in the sync comparison, Undo and imports).
- **Numbers:** no number without a source; conventions are labelled as conventions in a tip and here under Evidence base. Trends are never shown as a 1RM; a muscle with no clear lift reads unclear, never 0%; weight lifted is never a percentage against last week; no projection anywhere (r41). Deloads and lighter loads are whole steps, never under the bar on a barbell lift typed as the total. Sessions that are deloads, lighter or trimmed never set targets or trends (`tagged`, `offSession`).
- **V's rulings on screen:** the Volume radar is drawn from what was logged, never the routine's plan, and always draws; no Planned chip on Stats; the plan's usual-range note is a quiet line on Plan, never a flag and never on Stats; no other app is named on screen; no wording about shared phones, someone else or another person; no Comeback (former bests); no restyle without V's direction; "on target", the 1RM display and mid-workout adjustments on by default are V's calls.
- **Copy:** short, plain, specific; the number and the action on screen, the reasons in a tip or How this works; no em dashes, hype or exclamation marks; the serial comma in any list of three; estimated minutes only through `estMin` ("~N min"); the first-run Set up page stays under 400 characters, lines of 45 at most (tests/r21.js).
- **Phone:** 44 px touch targets, no sideways scroll at 320 px, light and dark both checked.
- **Code:** edit `src/`, then `npm run join`; never edit `index.html` by hand. Never reuse a class name the app has (`.tv`). Image tags in the script are written `\x3cimg`. Claude-only code is marked `/*ai{*/ ... /*}ai*/`. Any new inline script, outside host or `eval` needs the Content Security Policy changed with it. Keep `window.__ironlog`. Baselines are never deleted.
- **Tests:** never weaken or delete an assertion to make it pass; a new behaviour gets a suite that fails on the build before it. Suites reach no outside service.

## Commands

```
npm install
npm run setup     # installs Chromium for Playwright (once)
npm test          # every suite, then the user-facing ones again on dist/, side by side (r44); must end with "All suites passed"
npm run build     # writes dist/ only
npm run join      # writes index.html from src/ (after any edit in src/)
```

Run a single suite with `node tests/<name>.js`. Each suite prints `ok`/`FAIL` lines, then `ALL PASS` (the fuzz suite prints `fuzz clean`).

The suites and what each checks: `tests/SUITES.md`.

## How the code is organised (search for these names)

- **New-install layout (r28):** `DEFAULT_HIDDEN` and `DEFAULT_ORDER` seed only a fresh state (`normalize(null)`: a new device, Erase everything, Sign out and remove). `normalize` reads a missing `autoDone` or `hidden` in an older save as the app behaved before (off, none), and adds `secOrder` after the other keys, as older builds do, so the synced settings keep one key order across builds (a different order made r21 and r28 phones rewrite each other's core; tests/r22.js caught it). `moreLine(tab)` ends a tab that has hidden sections (`secShow`, `goLayout`; `MORE_LIVE` skips sections that would be empty); `layoutDefault` and `layoutReset` go back to the defaults. Simple view (`SIMPLE_HIDE`) is gone. `demoKeep`/`demoRestore` (`KEY+'.demoSettings'`): demo data loaded on a first run puts the settings back when it is cleared.
- **State:** `freshState()`, `normalize()` and `STATE_VERSION`. `normalize()` runs on every load, import and cloud merge, and it validates every field. Since r43 every record it rebuilds goes through `keepExtra(src,out,known)`: a field this build does not know is kept as plain JSON (names `okExtraKey`, at most `EXTRA_KEYS` fields and `EXTRA_MAX` characters, names included, per record, never read), and a record that kept one takes the key order it came in, since sync documents are compared as written and a different order would make two builds rewrite each other on every pull (the r43 review), so an older phone no longer drops what a newer build added; `known` (`KNOWN_ITEM`, `KNOWN_CARDIO`, `KNOWN_MEAS`) names fields written only when valid, so an invalid one is dropped. An edit from History carries the session's and each exercise's unknown fields, exercises matched by lift in order (`ACT.finishNow`); the exercise editor works on a deep copy, so it keeps them. Phones on r42 or older still drop them, so a new field still needs every device updated before it is relied on. Any new field needs a default there. New optional fields stay `undefined` when unset, so existing record hashes don't change and cloud sync doesn't treat old records as edited. A migration is a `version < N` block that only adds data and never overwrites a value the user set.
- **Storage:** localStorage key `ironlog.v1`. **Cloud sync:** `cloudInit`, `cloudPull`, `cloudFlush`, `mergeChunk`, through `cloudProvider()` (Claude's db inside Claude, `window.ironlogCloud` in the standalone app). Data is split into `core`, `draft`, half-month session chunks `s-YYYY-MM-N` and, since r22, yearly body documents `b-YYYY` (bodyweights and measurements; `bodyChunkOf`), with a per-record three-way merge. Core still carries `bodyweights:[]` and `measurements:[]`, empty, in r21's key order, so an older build writes it back unchanged. Builds before r22 ignore `b-` documents and still write weigh-ins into core: `legacyBody`/`absorbLegacy` pick those up and move them; the first time a device sees a `b-` document its base comes from its pre-r22 core base (`legacyBodyBase`, `baseFor`), so deletes made on a device that updated first stay deleted. While an r21 phone is still in use, a delete or correction made on that phone is not applied on r22 phones (add-only pick-up); update every device.
- **Analytics:** `IDX()` builds everything once per change (`invalidate()` clears it): `byEx`, `exStats`, `weekSets`, `weekHard`, `dayMus`, `dayMeta`, `prs`, `scores`. Read from `IDX()` rather than recomputing, so the headline numbers and the detail sections can't disagree.
- **Math:** `e1` (Brzycki up to 10 reps to failure, Epley at 11–12, none above 12; sets above RIR 4 excluded), `e1inv`, `rtfAt`, `rtfBand`. `calStats` and `rirEff` handle RIR calibration: shrink n/(n+3), cap ±2, 12-week window, compound vs isolation, applied only to sets at RIR ≤ 4. Also `suggest` (double progression), `progStep` and `jumpCap`, `recovery`, `rankDays`, `rankExercises`, `setSecs`/`setupSecs`/`dayMinutes`.
- **Load meaning:** `loadMode` (each / total / side / stack / bw; an assisted lift, `ex.assist`, is a bw lift whose sets store bodyweight minus the machine's help as a negative `w`: the field shows and takes the help as a plain number via `loadIn`, labels read BW−40, and `suggest` lowers the help to progress and raises it for a deload; `normalize` allows `w` down to −300 for this), `loadWords`, `loadNote`, `loadHead`, `lmChips`, `tonnage`. Every set stores the number exactly as typed. Estimates and targets stay in that frame, and tonnage counts what actually moved.
- **UI:** `render()` rebuilds `#view` from strings, with the views `viewToday`, `viewLogger`, `viewProgram`, `viewDash`, `viewHistory`, `viewSettings`. `sec()` is the one foldable section component; every section starts folded each visit except Sessions on History (`MAIN_FIXED`, `openMain`). Since r28 a section's explanation is `helpLink` (How this works) as the first line inside it, never a ? in the header beside the arrow; folds inside a section (`.subsec`) sit on their own surface. Actions are `data-act="name"` handled in the `ACT` object. `renderModal`/`renderModalBody` draw the sheets and keep their scroll and focus across re-renders.
- **Look:** tokens on `:root` (light) and the dark blocks. The Today card uses `--hero`, `--on-hero`, `--hero-bg`, `--hero-ring` and `--hero-shadow`, light in the light theme since r21; the rest-timer bar uses `--dock`, `--on-dock` and `--dock-bg`, inked in both themes. `--volt` is the accent and means go, done and progress; `--volt-line` is its thin-line form. The accent is chosen in Settings > General (`ACCENTS`: Ember, the default since r37 (`ACCENT0`; nothing stored reads as Ember), Blue, Volt, Pink) and applied as `data-accent` on `<html>`, which swaps `--volt`, `--on-volt`, `--volt-line`, `--volt-soft` and, for Blue, turns "above target" (`--blue`) violet so it never reads as done. Gold (`--gold`) is only for PRs. Green, amber, blue and red keep their meanings. Dark is the default for new installs. The r20 design layer: `--btn`, `--field`, `--card-b`, `--glass`, `--hero-bg`; sections unboxed with sentence-case titles; frosted header and tabs.
- **Undo:** `snapshot(inv)` records the state before an action; the first save after it records the result. Since r22 the stack is kept in IndexedDB (`ironlog-undo`, `undoPersist`, `undoRestore` on boot, entries over 7 days dropped), so Undo in Settings works after the app is reopened; `inv` functions are not stored, those entries undo through the merge. `undoForget` clears it when a signed-out phone removes its log. `ACT.undo` runs `inv` when given (in-session actions: remove exercise, remove logged set, swap), else a three-way merge (per exercise for the session in progress, `mergeDraft`), so work logged after the action survives.
- **Targets per day's range (r27):** `suggest` reads the sessions logged in the exact rep range the plan asks for (`rr`), so a lift on a heavy and a light day progresses per day, while that range is in use (its newest session within 42 days of the newest full session); sessions with no range on record go with them. Otherwise, a range new or not used lately, it reads every full session (the newest wins). The Last line follows the same choice. `planFor(exId,R,dayId)` prefers the day being trained.
- **Well past the range (r27):** every top set 2+ reps over repMax (a range moved down) sets the load from the e1RM estimate for the middle of the range, capped by `jumpCap`, whole steps; since r31 `fitE` reads sets past 12 reps to failure with Epley up to 30 for this, so a set of 25 still sets the load. A load step of 0 is a fixed load (the at-cap reps branch, `capped` only at a real cap).
- **Grey reps after a new load (r27):** when `b.tgt.kind==='load'`, `greyR` skips last time's reps (they were at the old load) and uses the set above, else the target's repMin.
- **Steps and lighter loads (r27):** `stepRead`/`unitStep`: either unit's default (5 lb or 2.5 kg) reads as the current unit's; any other step as typed. `lighterLoad(ex,plan,from,to)` steps down from `from` in whole steps of `incOf` (never under the bar on a compound barbell lift typed as the total), used by deloads, warm-ups (inserted after the existing ones, climbing) and drop sets.
- **Changes reach the session (r27):** `refreshEx(exId)` (load step sheet, heaviest load, exercise editor) and `syncDraftPlan(f)` (a Plan item's range, RIR, rest or step, on the day being trained) re-read targets for exercises with no set done; typed loads are never touched. `swapPlan(p,from,to,R,dayId)` gives a swapped-in exercise its routine plan, or its own default when timed differs, else the slot's; set count kept.
- **Custom setup in the numbers (r27):** `ex.kind` ('compound'/'iso', the editor's Movement) overrides `autoCompound`. Stalls need the last session within 42 days of both today and the newest session, and a live, unarchived exercise. `muscleStatus` treats a 0 minimum as met. `planHard(it)` (RIR 3 or less, or RIR off) for planned hard sets; `planSetsPerWeek(R,deload)` halves per item. `weekRoutine(ws)`/`weekNeed(ws)` score a past week against the routine most of its sessions used (streak and adherence). Pick for me halves sets in deload and lighter sessions.
- **Last time and targets (r26, V's rule):** `lastOf(all,base,fmt)` builds the Last line from the most recent session with the exercise (in the day's range while it is in use, r27), whatever kind it was, and labels it trimmed, lighter or deload. Targets still come from the last full session (`suggest` skips cut, lighter and deload sessions); when that is an earlier session, the block keeps its date in `basis` and the target shows a tip naming it. Last time's reps follow the shown session, except after a deload, whose reps were cut on purpose.
- **Last time's reps:** `lastRFor(b,si)` maps a row to last session's working sets (warm-ups and drop sets excluded); never index `lastR` by row.
- **Past workouts (r21):** `ACT.pastOpen` (an empty past day in the week bar, or History's Log a past workout) opens `pastSheet`: a date, then the routine day that was due (`pastDue`, from `cycleState(R,asOf)`, or the weekday) first, other training days, Freestyle. `pastDraft` builds a draft with `past:true`, `startedAt:null` and blocks from `newBlock(...,{before:date})`. `suggest(...,{before})`, `livePR(exId,s,date)` and `lastNoteOf(exId,before)` read only sessions up to that date (`statsUpTo` rebuilds the bests). Quick entry: no check-in, no rest timer or its buttons, typed reps tick the set. Changing a draft's date re-reads its targets (`refreshBlock`). Sessions sort by date everywhere, so one entered late lands in order.
- **Grey reps and Discard (r21):** `greyR(b,si)` is the number an empty reps field shows and the checkmark, auto-mark and the keyboard's Done take: last time's reps, else the working set above in this session, else the bottom of the planned range; `refreshGrey` updates it as reps are typed. `draftEntered(d)` says whether anything was put in (ticks, typed reps, cardio minutes, exercise notes, session notes other than `note0`, the text the app wrote); Discard (top and beside Finish) and replacing a session ask only then.
- **Logger flow:** a finished exercise folds to one line (`blockDone`, `autoFold`, `ui.blkOpen`); ticking done on an empty reps field logs last time's reps (`lastR`); RIR is a 0 to 5 strip (`rirSelect`, `rirShowStrip`, `ACT.rirPick`) that opens when the set's RIR box is tapped, and after each ticked set only when `settings.rirAsk` is on. Loads come prefilled from `suggest()`; with no history, a load typed on a working set fills the empty loads below it (`carryLoad`, and rows it filled follow a correction). Auto-mark (`settings.autoDone`, on for new installs since r28, off for older saves): typing reps and leaving ticks the set, and the first tap on that set's checkmark within 15 s (until another set is touched) confirms it rather than unticking it (`lastAuto`); leaving an empty reps field (Next, the iPhone keyboard's Done, a tap on blank space) accepts the grey number (`acceptGrey`, the `focusout` handler); moving within the row or tapping a button does not. `rebuilding` is true while `#view` is replaced, so the change the browser fires for a removed focused field never ticks a set. − Set on a row with reps typed, and removing a filled cardio entry, give an Undo; empty ones go quietly.
- **Updates (standalone app):** the service worker made by `scripts/build.js` precaches past the HTTP cache, and a new version waits instead of taking over. The build's boot script calls `ironlogUpdateReady()`, which shows `#updbar` ("New version ready", Reload, Later); Reload saves, then `ironlogApplyUpdate()` lets the waiting worker take over and the page reloads once. It also checks for updates whenever the app returns to the foreground.
- **Privacy:** `privacyLine()` in Settings > Your data says where the log lives and who can see it: this device, the Ironlog account (you and the app owner), or the Claude account inside Claude.
- **Bodyweight PRs (r32.1):** `prLoad(ex,s,date)` is the load PRs are judged at: on a bodyweight lift, the latest weigh-in times its share plus the added load, the same for every session; otherwise `loadOf`. Each point in `byEx` carries `pl`, and each exposure `pb`/`pbb` (the best estimate and its band at `pl`; equal to `best`/`bb` on a loaded lift). The PR list, `byBand`, `livePR`, `refreshPR`, `prBeat`, `allTimeBests` (records and heaviest) and the timed headline read those; estimates, trends, charts and `best`/`bestAll` keep each day's bodyweight.
- **A close variation's first session (r32.1):** `kinOf(ex,T)` finds the newest related lift (same free-weight `equip`, `loadMode`, `perSide`, one-sided by name `KIN_UNI`, `primary` and `patternOf`; not bw, assisted, timed or `noE1`) with a full session in the last 120 days; `kinStart` turns its working sets' `fitE` into a start (90%, 80% on a compound lift, middle of the range at the plan's RIR plus 1, down to the step or the related lift's `rackStep`). `suggestCore`'s no-history branch uses it (returns `kin`) before the first-time line.
- **What suggestions are (r31.1, V):** `SAFETY_TXT` (estimates from the lifter's log, not medical, physical therapy or coaching advice, can be wrong; technique, safety bars or a spotter, stop on pain, a doctor before starting or changing training; own risk) sits behind an i in three quiet places: `safetyLine()` under the privacy line in Settings > Your data, `#obSafety` on the first-run Set up page ("Suggestions are estimates, not advice.", short for r21's 45-character lines), and the first line of the Guide's How targets are set. Keep it short on screen; it is a notice, not legal advice, and a Terms page reviewed by a lawyer is V's call (PENDING 189).
- **Confirming with the code (r45, item 61):** `codeField(m)` on the waiting sheet and on sign-in after "Confirm your email first" or when the wait gives up (`m.needCode`); `ACT.acctCode` sends digits only to `ironlogAuth.verifyCode` (`verifyOtp`, type `email`; `signup` is deprecated there), owns the success path (the poll held off with `acctWait.busy`, the sign-in event's wait branch standing aside on `acctWait.coding`), and on any error tries the password once, since a link opened first uses the code up. `ACT.acctResend` → `resendCode` (`resend`, type `signup`, with the build's own redirect, so the preview's link returns to the preview). `friendly` gives a wrong, used or expired code one message (the service answers all three alike, `otp_expired`) and the once-a-minute limit as "Wait N seconds". Go in the code field confirms with the code (`acctSubmit` and the form's submit route it). Needs OWNER.md C6 (the code in the email template). The same lift again later in a session shows dashes in the Last column and the whole Last line, and `lastRFor` offers it no grey reps from last time (the set above or the range's bottom instead, no Copy last) (`lastDup`, keyed like `sameExOnce`), since how last time's sets split between the blocks is not recorded. `acctCode` waits for a poll already signing in before it tries the code, and gives up with "Still checking" if it is still running after 5 s. ## Rules for changes

1. Don't break what works. Run `npm test` before and after. Add or extend a suite for every behaviour you change.
2. Never lose data. Any change to stored shape needs a `normalize()` default, and a migration if it changes meaning, plus a case in `tests/migration.js`.
3. The math follows the evidence review summarised under "Evidence base" below. Don't change a number without a source. Label conventions as conventions, in a tip.
4. Copy is short, plain and specific. No em dashes, no hype, no exclamation marks. The default screen shows the number and the action; the reasoning goes in a `data-tip` or a `?` help toggle.
5. Phone first: 44 px touch targets, no horizontal overflow at 320 px, and light and dark both checked. `tests/charts-layout.js` checks overflow.
6. Code comments explain why, not what, in full sentences. That is the house style of this file.
7. Bump `APP_VERSION` for every published build, and `STATE_VERSION` only when the stored shape changes.

## Evidence base (behind the r13 corrections)

- **1RM:** Brzycki up to 10 reps to failure, Epley at 11–12 (they agree at 10). Nuzzo 2024 and Halperin 2022 on how estimates spread at higher reps.
- **Hard sets:** RIR ≤ 3 (Robinson 2024, Refalo 2023).
- **Target RIR of 1 (a convention, r29.5):** hypertrophy improves as sets end closer to failure (Robinson 2024, Sports Medicine meta-regressions), but training to failure grew the quadriceps no more than stopping at 1 to 2 RIR in trained lifters, with more velocity and rep loss (Refalo 2024, J Sports Sci). 1 sits between; templates use 0 on some isolation lifts and 2 on some heavy or bodyweight lifts. Helper muscles count 0.5 (Pelland 2025).
- **Blank RIR (a convention, r20):** RIR is optional. A blank is read as the lift's usual RIR, the median of its rated working sets in the last 12 weeks once there are 3 (`rirUsual`, `rirEst`), for e1RM, PRs, stalls and hard sets; with fewer, it counts as hard and as 0 for estimates (errs low). Recovery, calibration and the light-load recalibration read only entered RIR. People under-call reps left by about 1 on average (Halperin 2022), so a called 0 is kept as a call.
- **Weekly and per-session volume:** major-muscle bands of 10–20 are typical, not a ceiling. The per-session flag sits above 11 sets (Remmert 2025, preprint).
- **Deloads** round down to a loadable step, so they never land back on the full load: whole steps of the exercise's own step, never under the bar on a compound barbell lift typed as the total (r27; curls on EZ or fixed bars and per-side numbers have no floor).
- **Well past the range (a convention, r27):** uses the same e1RM estimate and 10% cap (`jumpCap`) as the RIR recalibration; no new number.
- **Moving and stalls:** "moving" needs ≥ 3% and a slope whose two-sided 80% interval (Student's t, n−2 degrees of freedom; `t90`) is above zero; estimated 1RM varies 2–8% day to day (Sigvaldsen 2023). Muscle trends count only lifts that are moving or falling. A stall is a flat or falling slope over the last 6 sessions, widened to cover ≥ 21 days when 6 do not (at least 4 sessions).
- **Recovery tiers:** 1, 2 or 3 days by set count, +1 day after failure sets or a new lift, +0.5 after heavy hinges, Nordics or walking lunges, −1 if every set stopped at RIR ≥ 3. This is a rule of thumb, used only for ranking.
- **Training blocks and trends (conventions, r30):** a session is read as lighter at 10% or more under the load of its previous three and 7% or more under their reps-alone reading (a deload is usually about 10% off; day-to-day swings in estimated strength are 2 to 8%, Sigvaldsen 2023). RIR enters a trend only when rated on 80% or more of a lift's sets. Trends read up to 20 reps to failure with Epley (formulas spread past 12, so never shown as a 1RM, but one lift against itself at similar reps still shows direction). A rep PR counts at 90% or more of the strongest set before it. An exercise with fewer than half its sets done is trimmed. A harder bodyweight swap (`HARD_EX`) gets 3 to 6 reps. None of these moves a number in the evidence above.
- **Tracked-only muscles (a convention, r29):** serratus, rotator cuff, neck and tibialis (`TRACK_ONLY`) are counted and shown with no target: no study sets a weekly dose for them, and most routines leave them to indirect work.
- **First-run targets (a convention, r29):** picking a ready-made routine on a first run lowers each weekly minimum to what it plans, only while every target is still the default and never raising anything; targets the lifter set are left alone. It moves no number in the evidence; it says the plan is the lifter's target, and the toast says so.
- **Second review conventions (r31):** the working load is the load done for the most sets among loads at 60% or more of the session's heaviest; flat is under 0.1% a week; a new level is lighter sessions in a row over 2 weeks or more; a trend needs 3 sessions over 2 weeks; load-finding reads sets past 12 reps to failure with Epley up to 30 (never shown) and allows a 25% jump in a lift's first 3 sessions; only compound lifts with an estimate count toward a deload suggestion; a routine made from an import uses the common ranges nearest the usual reps (1-3, 3-5, 6-8, 8-10, 10-12, 12-15, 15-20). None moves a number in the evidence above.
- **Third review conventions (r32):** a Lighter day or deload is 90% of the normal day's load (or last time's, if lower); a step is large when the estimate says it costs 1.5 reps or more, and then reps build first, up to a quarter of the top of the range past it; one set under the range among the others counts as the bottom of the range; four sessions in a row under the range at one load drop it; a fixed-rep plan (range under 3 reps wide) steps up whatever the step costs; a stall's slope is the median of pairwise slopes; a muscle's trend counts lifts with 4 sessions over 3 weeks; a PR is counted when the set is stronger than every earlier one by the rep-PR score; a dumbbell or kettlebell step is the largest common rack spacing the logged loads fit. None moves a number in the evidence above.
- **RIR 4 to 5 as half a set (a convention, r40, a setting off by default):** growth rises as sets end closer to failure (Robinson 2024), so sets further away still do something; half is a convention, not a measured dose. It moves weekly sets and targets only.
- **Bodyweight share:** only the push-up figure is measured (64%, Ebben 2011); the rest are segment-mass estimates.
- **Back after a break (a convention, r34.2):** a lift more than 28 days off starts at about 90% of its last working load with 2 or more reps in reserve: strength is largely kept for up to about 4 weeks without training and falls faster after (Bosquet 2013, a meta-analysis of training cessation). 90% is the same lighter-day number as r32, not a new one. Every set at 5 or more RIR steps up at least once, since 5 is the top of the scale and only a floor for the estimate.
- **Your pace (a convention, r43):** the time model (40 s a set and so on) is itself a convention; once 3 sessions are timed, estimates scale by the median of how long yours took against it, over the newest 8 in 12 weeks, leaving out a third or three times the model as a clock left on or stopped. It moves minutes only, never a load, a rep or a set.
- **Your training (r44):** heavier loads gave more strength for similar growth (Schoenfeld 2017, meta-analysis of low vs high loads; ACSM 2009 position stand, 1 to 6 RM for strength past the novice stage, 8 to 12 RM for novices), and 3 minutes' rest beat 1 for strength and size (Schoenfeld 2016). 5 to 8 for Both, 2 in reserve on heavy compounds, and 3 or 2 in reserve for a first year are conventions. Focus muscles: more weekly sets grow a muscle more (Pelland 2025); 30% up is a convention; the rest at a third of the minimum is maintenance (Bickel 2011; Spiering 2021 review). The strength focus's 5 days and 3% are conventions (3% is the app's own threshold for a real change).
- **Waist-to-height:** 0.5 / 0.6 bands (NICE 2022).
- **Tape measurements:** changes under about 1 cm are treated as noise.
- **Long-length bonus:** only for exercises backed by trials (seated leg curl, overhead triceps, standing calf raise) or by mechanics (labelled as such).
