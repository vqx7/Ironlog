# Architecture

Where Ironlog's code is going, how it gets there, and the rules that hold on the way. Written in r49 (V, 2026-10-16: real modules, one source for every value, no hard-coding, built like a professional codebase). PENDING item 303 tracks it.

**Since r54 (V, 2026-10-18, PENDING 316).** The token-for-token move check (`tests/moved.js`) and the planted-bug testing of the checks are retired: what they proved through r53 stays proved, and code from here is held by the behaviour suites, the type checker and the rules in `tests/hygiene.js` (layers, no `any`, commented casts and exports, nothing behind the model's back, the ratchet below). Legacy code may be fixed in place with a failing test first; a screen being changed substantially moves into `src/app/` as a whole. Where the sections below describe `tests/moved.js`, its `edits` or the statement-for-statement hold on the legacy script, they record how phases 2 to 3b and r53 were proved, not a rule in force.

## Why

Ironlog started as a Claude artifact, which has to be one HTML file. When the artifact was retired on 2026-09-27 the code stayed in that shape: one script, every function and value in one shared scope, screens built from HTML strings. r36 cut it into 24 files, but they are pieces of one script, not modules. In that shape any part can read or change any other part, a value can be typed in many places, and nothing but the tests stops either. Typed modules with clear boundaries stop both before the app runs.

- **TypeScript**, strict, checked on every test run (`tests/hygiene.js`).
- **esbuild** bundles it into the one inline script the page needs. Every suite opens the page as a file, where module scripts are refused, and the installed app's Content Security Policy fingerprints each inline script, so the output stays one inline script. A larger toolchain such as Vite (a dev server, with Rollup or Rolldown for production) would add nothing this app uses.
- **Modules with one-way dependencies**: config at the bottom, then data, engine and analytics (pure functions of their inputs), then storage and sync, then the screens. A module never reaches into another's internals. Every file under `src/app/`, at any depth, is a `.ts` module named by its path, in a move or written new, formatted by Prettier, with a comment on every export. Since r51 `tests/hygiene.js` holds each module to its layer in the list below, the one place the layers are written: an import goes only to the same layer or below, a new module is added to the list, and no import goes round in a circle (the bundle turns a module's `const` into `var`, so in a circle a value read before its module has run is `undefined`, not an error).

Layer 0, config and record shapes: config, types
Layer 1, data: util, units, library, routines, formulas, records, gym, profile, model, layout
Layer 2, engine and analytics: session, loads, prs, trend, volume, goals, importing, format, charts, analytics, time, weeks, coach, engine, plans
Layer 3, storage and sync: chunks, merge, store, live, providers, normalize, storage, sync
Layer 4, screens: icons, feedback, effort, guide, sheets

- **Screens as components**, one per tab, reading copy and labels from one place.

## How it gets there: the legacy code shrinks

The current code is the **legacy script**: `src/10-*.js` to `src/29-*.js`, joined in name order, still wrapped in its original `(function(){ ... })()` so every `const` and `let` behaves exactly as written. `scripts/join.js` puts `src/09-imports.js` before it: the real `import` lines through which the legacy script reads what has moved to `src/app/`. Each phase moves code out of the legacy parts into modules and deletes the old copy in the same change, so nothing exists twice.

`scripts/depmap.js` parses the legacy script and lists every top-level declaration, what it uses, which values are shared mutable state, and which declarations are pure (no browser, no shared state, all the way down) and can move as they are.

**The ratchet:** the legacy script may never grow. `tests/hygiene.js` fails when it has more top-level declarations or more lines than the numbers below, and also when it has fewer, until the numbers are lowered to match, so each phase locks in what it moved. A change that adds code adds it in `src/app/`.

## The phases

Each phase is its own pull request, tried in the preview before V merges it. Each proves it changes nothing a lifter sees: the full suite in Chromium and WebKit, `tests/coherence.js`, and for the engine and analytics the 2,000 seeded histories of `tests/r36.js` giving identical numbers before and after (since r53, but for what r53 changes on purpose: its PRs on lighter and deload days taken out, the coach compared as r53 changes it, and a history where a tagged lift counts in full counted and left to `tests/r53.js`; `tests/r53w.js` holds each of r53's differences from r52 to the rule that makes it).

1. **Toolchain and config (r49).** esbuild, TypeScript, `src/app/config.ts`, the version people see (2.0) apart from the build, the single-source and boundary checks, the ratchet. Done in r49.
2. **Pure math and data (r50).** The bottom layers, 109 declarations that read nothing but their arguments, each other and (for `uid` and `today`) the clock and a random number: `util.ts` (text, ids, dates, numbers, the sync hash), `units.ts` (units and plates), `library.ts` (muscles, joints, equipment, the exercise library and what an exercise is), `routines.ts` (the default plan and the ready-made routines) and `formulas.ts` (the 1RM estimate and its inverses, the working load, set counting, the time model and the thresholds behind trends and breaks). Moved as they were: `tests/moved.js` compares each with the same declaration in r49 after esbuild's printer, so types and layout are free and every expression and literal must match, and a one-value change fails it; it also holds every name the moved code uses to what it meant in r49 and allows nothing else at a moved module's top level (an independent review found five ways to change behaviour that passed a comparison of text alone, and each now fails). The bundle gained a "use strict" at its top: the modules ran in sloppy mode inside esbuild's wrapper, where ES modules are always strict. The pure functions that still read a setting or the log (the load step in the unit on screen, the analytics) wait for phase 3. Done in r50.
3. **State with one owner**, in two releases (V, 2026-10-17: six releases from here, grouped only where grouping adds no risk).
   - **3a (r51): the rest of the self-contained code, and one owner for the shared state.** Done in r51, as planned below.
   - **3b (r52): the engine and analytics take what they read as arguments.** Done in r52 (pull request #45, merged by V on 2026-10-18) as planned below (Phase 3b in detail), with what the building found after the plan. `suggest`, `IDX()` and the readers around them stop reaching for `state` and the settings and are passed them, so they become pure functions with unit tests of their own; `tests/r36.js` (2,000 seeded histories) proves every number unchanged.
   Between 3 and 4, **r53 is a behaviour release, not a phase**: V's rulings of 2026-10-18 and the audit's fixes, each change to moved code made through the move check's own `edits` (r53 in detail). **r54 is one too**: the whole-app audit's fixes, made under the way of working V approved on 2026-10-18 (r54 in detail).
4. **Storage and sync (r56), alone.** Done in r56 as planned below (Phase 4 in detail). Same storage keys, same sync documents, same key order: `tests/r56.js`, `tests/seams.js`, `tests/migration.js` and every baseline hold them to it. Nothing rides along: a fault across devices must have one suspect, and the log is the one thing that cannot be repaired afterwards.
5. **Screens (r57 to r60).** As components, two tabs a release: Settings and History (r57), then Plan and Stats (r58), then Today (r59, with looking ahead in the week bar and the calendar, PENDING 329), and the session screen last, alone (r60), since it is used mid-workout. The legacy script is deleted when it is empty.

**How these reach V (V, 2026-10-20: "finish fix validate verify optimize ... through to 59/60", without a preview check for each).** Each release is its own branch and pull request, built on the one before (r56 on r55.1, r57 on r56, and so on), each with its failing-first tests, a lifter-journey audit, one independent review and every suite green in Chromium and WebKit, and its pull request saying which one it follows. V merges them in order on GitHub's website; after each merge the next pull request's base is changed to `main`.

1. **One workout open on two phones (328 a and c).** The session in progress is one document, merged whole: of two copies edited since they last agreed, the later edit replaced the other, and the loser's ticked sets were gone on every phone. Now its merge base keeps the content, not only a fingerprint: the draft's sync note holds the copy both sides last agreed on (`Base.draft`, beside `d`; a note an older build saved has none, and merges as before until the next agreement). `mergeChunk('draft', ...)` then merges two copies of the same workout (the same session id on both sides and in the base) exercise by exercise and set by set, as Undo's `mergeDraft` merges by exercise: exercises keyed by exercise id and occurrence (`exId#n`); a set judged by its row (the rows both phones started from are the base's; a row added on one side alone is kept after the base's rows, local's additions first; a row removed on one side alone goes, unless the other side changed it, since keeping data is the recoverable mistake); a set changed on one side alone takes that side, changed on both takes the later edit (`remoteWins`) and counts a conflict; a block's own fields (its note, its adjustment, its marks) and the workout's (its notes, day name, marks, check-in, cardio rows) are merged value by value against the base (`merge3Val`). Two copies of different workouts (one phone finished or discarded and started another, or two started apart) still take the later edit whole, as before, and the copy that loses is never dropped: its ticked sets go into the log as a session, with its cardio rows and check-in, exactly as a first link keeps another phone's workout (`draftSession`, `draftCardio`, r55), and the toast says so ("...replaced by the one on another device. Its ticked sets are saved in History."). An edit of a saved session in progress (`editingId`) is one record, as now: the saved session it edits is already kept. Where it bites: `applyChunk('draft')` in a flush and the adoption of the draft document in a pull both go through one function (`takeDraft`) that saves the losing copy's sets first. The first tests: the audit's reproduction (327) and the review's (328 a: a first link keeps the new phone's workout, the account's phone ticks a set before its next pull; 328 c: a set ticked while signed out on a workout another phone also ticked).

2. **A phone holding another account's log (328 b, V's call of 2026-10-20).** A phone signed out of one account and signed in to another merged the first account's log into the second as a first link. Now `cloudInit` reads the notes before it would clear them: the notes belong to another account (`cloud.acct` set and not this account) and the phone holds a log (`realCount`, weigh-ins, tape entries, cardio, a workout in progress, a custom exercise or a routine that is the lifter's own, as the first-link test reads it); then nothing syncs until the lifter answers one sheet: "This phone holds a log from another account. Add it to this account, or use this account's log?", with Add it, Use this account's log, and Cancel. Add it: the notes are cleared and the sync starts as a first link, the merge as it is. Use this account's log: the phone's log is kept aside first, whole, under a key of its own for the account it belongs to (`KEY.aside.<account>`, through `storage.ts`, with the notes that go with it), so what only this phone holds is not lost: the next sign-in to that account on this phone finds it and merges it back as a first link, and Your data lists it until then; then Undo is cleared (a step held the other account's log, and undoing it would sync that log into this account), the notes are cleared, and the sync starts on a fresh state, which adopts the account's copy. Cancel: the notes stay as they were, the sync stays off, and the sign-out goes through the account service alone (`AUTH().signOut()`), never `cloudStop(true)`. While the question is open every other start of a sync is held (`cloudInit` returns at once, `acctRetry` too). An account the notes name that no longer exists is guarded the same way (the notes name it, the sheet still asks; Add it is the only safe answer the lifter needs, Use this account's log keeps the log aside under that id). A phone whose notes were forgotten (a restore, Copy my log in, demo data, Erase everything) has no account to ask about and is not asked, as now. The suites: the review's reproduction (a deletion made in the second account reaching the first), each answer, Cancel's state, a sync started while the question is open, the aside log merged back.

A cardio entry's kind and time are checked against the lists, not looked up (`CARDIOL[String(kind)]` let any key Object has, and a list, through).

4. **The sync's status as one set of states (307).** `cloud.status` is `'local' | 'connecting' | 'saving' | 'synced' | 'offline'`, moved only by `setCloud`; a string from anywhere else is refused by the type checker.

5. **A start time a Date can hold (308).** `normalize()` keeps a session's `t` and a workout's `startedAt` only when `new Date(t)` is a date (an integer, 0 < t <= 8,640,000,000,000,000), so a damaged save can no longer show "Invalid Date" in History; one that cannot is dropped, as any damaged field is.

### r53 in detail (a behaviour release between phases)

**Why it is not a phase.** V's rulings of 2026-10-18 change what a lifter sees: a day's label must not override what a lift did ("tied at exercise level"), a PR is a PR whenever it happens, and Finish's offer adds an exercise at its normal-day sets. The audit V asked for the same day added two: no stall while a flagged injury holds a lift's load, and the coach holding a deload back only after a lighter week, as its rule says. Phase 4 must change nothing a lifter sees, so these go first, alone.

**How the code changed.** Seven moved declarations changed through `edits` (A change to the legacy script between phases, above): `idxPRsIn` (PRs on every day), `IDXIn` (one step added, and the PR list passed to the stall test), `idxAutoLighter` (its usual-load test read through the shared `atUsualLoad`, the same comparison), `idxLiftIn` (the injury, and a PR on a session left out of the stall's stretch since the third-last session of it counted as movement, on a lift with a reading only one Recent PRs lists, read from the PR list it is now given), `coachIn` (its stall tip's words), `recentLighterIn` (a lighter week read from what the lifts did: more than half its sessions with half or more of their lifts done lighter, once it has ended or from the second, or, a deload begun mid-week, its last two or more sessions deloads done lighter, tagged deload or in the marked week; rest weeks; a marked deload week with nothing trained in it) and `planForIn` (a lift on no day of the routine planned from its own last full session). Four were added with their exact code: `USUAL_SHARE`, `atUsualLoad`, `atUsualLevel` (as many sets as each of the sessions it is compared with first, then the load and the reading, or the reps where there is no reading) and `idxTaggedFull`. Seven legacy declarations moved: `routineUpdates` to `routines.ts` as `routineUpdatesIn`, to change (`moved: true`, its new code stated), with its adapter; `whyTarget` to `session.ts`, to change its note on what does not set a target (a session where the lift was trimmed or done lighter than usual, or on a lighter day, in a deload or on an exercise made lighter had fewer reps or sets than usual, no longer lighter and deload sessions as a whole); the Guide (`guideSheet`) to `guide.ts`, its text changes listed as pairs; and `AUTH`, `FB`, `rirScale` and `halfLbl`, which the Guide reads, to `providers.ts` and `effort.ts` unchanged. ## Rules (each enforced by a test, not by memory)

- Code that moves or changes is held by the behaviour suites, the screens' checks against each other (`tests/coherence.js`) and the type checker, and a change in behaviour gets a suite that fails on the build before it (since r54, V, PENDING 316). Through r53, `tests/moved.js` held every moved declaration to the build its phase started from, token for token, and the legacy script left behind to the baseline's, statement for statement; what it proved stays proved, and it was retired with r54.
- Moved code exists once: no legacy declaration takes a module export's name (it would hide the module's copy), every export the legacy script uses is imported, every import is used, and every name the legacy script reads without declaring or importing it is on a list of browser and JavaScript globals, so a missing import fails before the app runs (`tests/hygiene.js`, from `scripts/depmap.js`'s scope-aware reading of the legacy script). An imported name that is shared state (exported with `let`, or written by the legacy script) makes its readers impure in the map.

- A value that names, identifies or configures the app is defined once, in `src/app/config.ts`, and read everywhere else. `tests/hygiene.js` fails on the name, the site address, a build id or the storage id typed anywhere else, in code or markup.
- `src/app/` imports only `src/app/`. The legacy parts import only through `src/09-imports.js`.
- The legacy script never grows, in declarations or in lines (the ratchet above).
- Types say only what is true: no value in `src/app/` has a type that is any or holds it as a union member or type argument, by the type checker (within the reach item 1 of The outside review states); every cast and `!` has a comment naming it, and no cast's written type names a type parameter around it; the casts, `!` and open types only fall in number (the ratchet in The outside review); every `catch` in a module throws or carries a comment (`tests/hygiene.js`).
- Outside addresses, library versions, the font faces and their weights are config's, like the name, in the source, the scripts and the test fixtures; any other outside address waits in The outside review's list for its phase (`tests/hygiene.js`).
- Nothing a screen sets up outlives the render that drew it: charts, drag lists, intervals and the 3D body's one WebGL context (`tests/cleanup.js`).
- Storage keys keep "ironlog" whatever the app is called: they are built from `STORAGE_ID`, an identifier that never changes, since renaming it would leave saved logs behind. `tests/r49.js` holds the keys to their exact values.
- Moving code changes no behaviour: the suites and the coherence checks say so before a release is merged; the comparisons of whole builds stay pinned to the moves they proved, `tests/r36.js` (r35 and r52, the r36 split), `tests/r52.js` (r51 and r52, phase 3b, on wide histories, past midnight, with stale caches and on the demo) and `tests/r53w.js` (r52 and r53 the same way, each difference held to the r53 rule that makes it); and `tests/engine.js` runs the engine alone in Node against the page's answers, its lines run a ratchet above.
- The engine and the analytics read the log, the date and their caches only through the model they are given, all the way down: no clock, randomness, store, live model, page global or changing module value but the listed date formatters (`tests/hygiene.js`, rule 6). The code is read as written: `Date` only as `new Date(a date)`, `Date.UTC` or `Date.parse`, `Math` never as a value or `random`, no global read by a computed name, a formatter's `format` only called with a date written in place and never taken as a value, no module value written by name or by Object's own writers (`assign`, `defineProperty`, `defineProperties`, `setPrototypeOf`), and none made at load by running a function, whose closure could keep state. A value undefined only when it runs, a write through a local alias and a read built by reflection are beyond a reading of the code: `tests/engine.js` runs the engine with every module table frozen and the log watched for any attempt to change it, and review reads the rest. A function whose first parameter is `M` is read as one taking the model, and held to this rule with all it reaches.
