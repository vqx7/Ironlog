# Architecture

Where Ironlog's code is going, how it gets there, and the rules that hold on the way. Written in r49 (V, 2026-10-16: real modules, one source for every value, no hard-coding, built like a professional codebase). PENDING item 303 tracks it.

**Since r54 (V, 2026-10-18, PENDING 316).** The token-for-token move check (`tests/moved.js`) and the planted-bug testing of the checks are retired: what they proved through r53 stays proved, and code from here is held by the behaviour suites, the type checker and the rules in `tests/hygiene.js` (layers, no `any`, commented casts and exports, nothing behind the model's back, the ratchet below). Legacy code may be fixed in place with a failing test first; a screen being changed substantially moves into `src/app/` as a whole. Where the sections below describe `tests/moved.js`, its `edits` or the statement-for-statement hold on the legacy script, they record how phases 2 to 3b and r53 were proved, not a rule in force.

## Why

Ironlog started as a Claude artifact, which has to be one HTML file. When the artifact was retired on 2026-09-27 the code stayed in that shape: one script, every function and value in one shared scope, screens built from HTML strings. r36 cut it into 24 files, but they are pieces of one script, not modules. In that shape any part can read or change any other part, a value can be typed in many places, and nothing but the tests stops either. Typed modules with clear boundaries stop both before the app runs.

- **TypeScript**, strict, checked on every test run (`tests/hygiene.js`).
- **esbuild** bundles it into the one inline script the page needs. Every suite opens the page as a file, where module scripts are refused, and the installed app's Content Security Policy fingerprints each inline script, so the output stays one inline script. A larger toolchain such as Vite (a dev server, with Rollup or Rolldown for production) would add nothing this app uses.
- **Modules with one-way dependencies**: config at the bottom, then data, engine and analytics (pure functions of their inputs), then storage and sync, then the screens. A module never reaches into another's internals. Every file under `src/app/`, at any depth, is a `.ts` module named by its path, in a move or written new, formatted by Prettier, with a comment on every export. Since r51 `tests/hygiene.js` holds each module to its layer in the list below, the one place the layers are written: an import goes only to the same layer or below, a new module is added to the list, and no import goes round in a circle (the bundle turns a module's `const` into `var`, so in a circle a value read before its module has run is `undefined`, not an error).

Layer 0, config and record shapes: config, types
Layer 1, data: util, units, library, routines, formulas, records, gym, profile, model, layout
Layer 2, engine and analytics: session, loads, prs, trend, volume, goals, importing, format, charts, analytics, time, weeks, coach, engine, plans
Layer 3, storage and sync: chunks, merge, store, live, providers, normalize, storage, sync, act
Layer 4, screens: icons, feedback, effort, guide, sheets, env, display, view, history, settings, graphs, plan, stats

- **Screens as components**, one per tab, reading copy and labels from one place.

## How it gets there: the legacy code shrinks

The current code is the **legacy script**: `src/10-*.js` to `src/29-*.js`, joined in name order, still wrapped in its original `(function(){ ... })()` so every `const` and `let` behaves exactly as written. `scripts/join.js` puts `src/09-imports.js` before it: the real `import` lines through which the legacy script reads what has moved to `src/app/`. Each phase moves code out of the legacy parts into modules and deletes the old copy in the same change, so nothing exists twice.

`scripts/depmap.js` parses the legacy script and lists every top-level declaration, what it uses, which values are shared mutable state, and which declarations are pure (no browser, no shared state, all the way down) and can move as they are.

**The ratchet:** the legacy script may never grow. `tests/hygiene.js` fails when it has more top-level declarations or more lines than the numbers below, and also when it has fewer, until the numbers are lowered to match, so each phase locks in what it moved. A change that adds code adds it in `src/app/`.

## The phases

Each phase is its own pull request, tried in the preview before V merges it. Each proves it changes nothing a lifter sees: the full suite in Chromium and WebKit, `tests/coherence.js`, and for the engine and analytics the 2,000 seeded histories of `tests/r36.js` giving identical numbers before and after (since r53, but for what r53 changes on purpose: its PRs on lighter and deload days taken out, the coach compared as r53 changes it, and a history where a tagged lift counts in full counted and left to `tests/r53.js`; `tests/r53w.js` holds each of r53's differences from r52 to the rule that makes it).

1. **Toolchain and config (r49).** esbuild, TypeScript, `src/app/config.ts`, the version people see (2.0) apart from the build, the single-source and boundary checks, the ratchet. Done in r49.
2. **Pure math and data (r50).** The bottom layers, 109 declarations that read nothing but their arguments, each other and (for `uid` and `today`) the clock and a random number: `util.ts` (text, ids, dates, numbers, the sync hash), `units.ts` (units and plates), `library.ts` (muscles, joints, equipment, the exercise library and what an exercise is), `routines.ts` (the default plan and the ready-made routines) and `formulas.ts` (the 1RM estimate and its inverses, the working load, set counting, the time model and the thresholds behind trends and breaks). Moved as they were: `tests/moved.js` compares each with the same declaration in r49 after esbuild's printer, so types and layout are free and every expression and literal must match, and a one-value change fails it; it also holds every name the moved code uses to what it meant in r49 and allows nothing else at a moved module's top level (an independent review found five ways to change behaviour that passed a comparison of text alone, and each now fails). The bundle gained a "use strict" at its top: the modules ran in sloppy mode inside esbuild's wrapper, where ES modules are always strict. The pure functions that still read a setting or the log (the load step in the unit on screen, the analytics) wait for phase 3. Done in r50.
3. **State with one owner**, in two releases (V, 2026-10-17: six releases from here, grouped only where grouping adds no risk).
   - **3a (r51): the rest of the self-contained code, and one owner for the shared state.** Done in r51, as planned (Phase 3a in detail, docs/ARCHIVE.md).
   - **3b (r52): the engine and analytics take what they read as arguments.** Done in r52 (pull request #45, merged by V on 2026-10-18) as planned (Phase 3b in detail, docs/ARCHIVE.md), with what the building found after the plan. `suggest`, `IDX()` and the readers around them stop reaching for `state` and the settings and are passed them, so they become pure functions with unit tests of their own; `tests/r36.js` (2,000 seeded histories) proves every number unchanged.
   Between 3 and 4, **r53 is a behaviour release, not a phase**: V's rulings of 2026-10-18 and the audit's fixes, each change to moved code made through the move check's own `edits` (r53 in detail, docs/ARCHIVE.md). **r54 is one too**: the whole-app audit's fixes, made under the way of working V approved on 2026-10-18 (r54 in detail, docs/ARCHIVE.md).
4. **Storage and sync (r56), alone.** Done in r56 as planned (Phase 4 in detail, docs/ARCHIVE.md). Same storage keys, same sync documents, same key order: `tests/r56.js`, `tests/seams.js`, `tests/migration.js` and every baseline hold them to it. Nothing rides along: a fault across devices must have one suspect, and the log is the one thing that cannot be repaired afterwards.
5. **Screens (r57 to r60).** As components, two tabs a release: Settings and History (r57, built 2026-10-24), then Plan and Stats (r58), then Today (r59, with looking ahead in the week bar and the calendar, PENDING 329), and the session screen last, alone (r60), since it is used mid-workout. The legacy script is deleted when it is empty.

### Phase 5 design (decided 2026-10-24, before r57)

The audit before the screens (PENDING 339 a to d) asked for three decisions before r57 sets the pattern every screen follows; V asked for the best judgement on them (2026-10-24).

1. **How a screen draws: lit-html,** pinned to one exact version in `package.json` and bundled into the page's one inline script by `scripts/join.js` (esbuild), the only package `src/app/` may import (`tests/hygiene.js`): no address loads it, so offline use and the Content Security Policy need nothing new, and its license ships in `LICENSES.txt`. It escapes every value by default (today safety rests on `esc` by hand and the escaping suite), updates only what changed, so a ticked set no longer redraws the session screen and its scroll and focus workarounds go, and needs no `eval`, so the Content Security Policy holds. A screen is a function of the state and `ui` that returns a template; one `render` puts the current tab's template in `#view`. A screen moves whole into `src/app/` in its release (layer 4), with its markup, its actions and its own typed part of `ui`.

   **As built in r57.** `view.ts` is the host: lit-html owns `#view` and draws every tab into it, a moved screen as its template (updated in place, so its elements, the field being typed in and its focus stay; a field's value is never replaced while it is being typed in, `fieldValue`), a legacy screen as its markup string, drawn fresh each time as innerHTML drew it (`drawLegacy`), so the moves that follow a legacy draw (`applySecOrder`, `applyHidden`, `openMain`, the drag lists) work on it as before. A moved screen places its sections itself, in the saved order with the hidden ones left out (`placed`), and opens them from `ui.folds` (`isOpen`, shared with the legacy script); a drag or an arrow key on one of its sections reads the new order, puts the section back where it was drawn, saves the order and draws the screen again, and a draw in the middle of a drag drops it, the section put back (`dragDrop`, from the page's teardown). The parts the moved screens share (`section`, `pageTitle`, `howLink`, `howText`, `tipButton`, `grip`, `tabFoot`, `labelTip`) draw the markup of the legacy helpers of the old names, which stay for the screens not moved yet and go with the last of them (r60); `tests/r57.js` holds History and Settings to r56.2's elements, attributes, field values and visible text. What History and Settings open or start elsewhere stays with that code, reached by the button's `data-act` as before, and moves with it: the sheets (the calendar, a past workout, import, backup text, the save kept aside, diagnostics, the guide, reports), the backup files, Install, Undo, demo data's Load, Edit and Do again (they start a workout), the account's own actions (sign in, sign out, delete), and the session's fill-in choice (`loadAsk`). The session's effects the moved screens call (`refreshEx`, `syncDraftPlan`, `unitWords`, the rest timer, the screen kept on) reach them through `fx` until the session screen moves (r60).
2. **One way to change the log:** typed actions in layer 3 (`act`), each doing, in order, the check, the Undo step, the change, the caches dropped, the save and the sync. The legacy script's direct writes, about 170 save calls and 41 hand-placed Undo steps, are replaced screen by screen as each moves, so by the end a change that skips Undo or the save cannot be written. r57 builds `act` (`src/app/act.ts`, with `toTrash`) and moves Settings and History onto it: `tests/hygiene.js` refuses a write to the log in a moved screen outside a function given to `act`, and a save, a saveSoon, a commit or an Undo step taken by hand; `tests/r57.js` reads every step on the page after each of their actions. An edit keeps no Undo step, as before r57 (Undo's button says edits are not undoable); `act` takes one where the action had one.
3. **One meaning each of best estimate, PR and usual** before Stats (r58) and the session screen (r60) are drawn on them: r56.2 made the best estimate one function everywhere (All-time bests') and a lifter's usual one rule for every day (PENDING 338); the PR notions (any, listed, announced) become two with Stats in r58. **As built in r58:** a PR is the counted one (`big`) on every screen that names one (Recent PRs, the counts, the recap, the toast and the row's mark, the Lifts chart, PR last time, Readiness), a heavier set that is not one Heaviest yet; the stall test alone reads any record (`progress`) as the lift having moved. **Added in r51, each a check that fails without it** (nothing a lifter sees changes):

1. **Types say only what is true**, read with the type checker, so an `any` is found where the word is not written: no name (a parameter, a variable, a destructured binding, any identifier read), call, await or property read in `src/app/` has a type that is any or holds any as a union member or a type argument (`any[]` from `Array.isArray` on an unknown, `Map<any, any>` from a bare `new Map()`, `any[]` from `Array(n)`), except an expression wrapped directly in a cast, which makes it explicit (`JSON.parse` is typed any). An any deeper inside an object's or a function's own type is beyond it. The other ways to tell TypeScript a type it cannot check count as casts: `as` (other than `as const`), a type predicate (`x is T`), and a parameter annotated where its contextual type is any, written in place as the callback (a `String.replace` callback's groups; typing one `unknown` hides nothing and is not counted; a named function passed instead is not read). A function, method or constructor declared without a body is refused: an overload's signature is not checked against the implementation (call signatures in an interface are not read). Every cast and every `!` (a non-null assertion, or a definite assignment such as `let x!: T`) has a comment naming it ("cast", or a `!` standing alone): on its own line, alone on the line above, or leading a statement that holds it. A cast whose written type names a type parameter of a declaration around it is refused, wherever in the type it is named (an object, a function, `keyof`, a conditional, a type argument) and through any alias, interface or `typeof` the type names, since one generic helper would turn any number of casts into calls the count never sees. The counts below are a ratchet, as the legacy script's size is: higher fails, and lower fails until the numbers are lowered, so a cast replaced by a real type stays replaced. Open types (an index signature, or a `Record` keyed by string, whose values are `unknown` or `any`), mostly on the shared state the untyped legacy script still writes, are counted the same way and close as their writers move. What a comment says, and whether one comment on a declaration rightly covers several casts in it, is review's to judge; the count shows any new one in the diff. The numbers were first set at 37, 24 and 6 and restated three times, in review, as the checker was made to see more: values typed any without the word became honest types (the import parser's regular-expression callbacks, `Array<string>(n)`, `new Map<string, ImpItem>()`, the copy of the default section order, `let rpe`), a generic cast became a plain return (`mergeDraft`, `trendW`), the definite assignment `let state!` began to count as a `!`, the twelve `Record<string, unknown>` as open types, the 30 hand-typed regular-expression groups and the two type predicates as casts, and the six `any[]` that `Array.isArray` leaves on an unknown became explained casts to `unknown[]`.

3. **An error handled in a module is logged, or carries a comment.** Every `catch` block in `src/app/`, and every handler given to a promise (`.catch(fn)`, `["catch"](fn)`, the second function of `.then`), ends in a throw (its own last statement, so not a throw that only sometimes runs or one in a nested function), logs the error (a statement of its own calling `log`, the error log in `storage.ts`, since r56, when `log` moved: not one in a nested function or that only sometimes runs) or holds a comment of its own (not one inside a function nested in it), read from the syntax tree, saying why the error is expected and what the fallback is; a handler must be written in place, so it can be read (one reached through `.call` or `.bind` is not read, and `cq`'s second handler is written out for it), and a `finally` may not return, break or continue, which would drop an error in flight. Whether the comment says why is review's to judge. Until r56 a module could not log, and the rule was a throw or a comment.

## Rules (each enforced by a test, not by memory)

- Code that moves or changes is held by the behaviour suites, the screens' checks against each other (`tests/coherence.js`) and the type checker, and a change in behaviour gets a suite that fails on the build before it (since r54, V, PENDING 316). Through r53, `tests/moved.js` held every moved declaration to the build its phase started from, token for token, and the legacy script left behind to the baseline's, statement for statement; what it proved stays proved, and it was retired with r54.
- Moved code exists once: no legacy declaration takes a module export's name (it would hide the module's copy), every export the legacy script uses is imported, every import is used, and every name the legacy script reads without declaring or importing it is on a list of browser and JavaScript globals, so a missing import fails before the app runs (`tests/hygiene.js`, from `scripts/depmap.js`'s scope-aware reading of the legacy script). An imported name that is shared state (exported with `let`, or written by the legacy script) makes its readers impure in the map.

- A value that names, identifies or configures the app is defined once, in `src/app/config.ts`, and read everywhere else. `tests/hygiene.js` fails on the name, the site address, a build id or the storage id typed anywhere else, in code or markup.
- `src/app/` imports only `src/app/` and lit-html, pinned exactly and bundled (r57). The legacy parts import only through `src/09-imports.js`.
- The legacy script never grows, in declarations or in lines (the ratchet above).
- Types say only what is true: no value in `src/app/` has a type that is any or holds it as a union member or type argument, by the type checker (within the reach item 1 of The outside review states); every cast and `!` has a comment naming it, and no cast's written type names a type parameter around it; the casts, `!` and open types only fall in number (the ratchet in The outside review); every `catch` in a module throws or carries a comment (`tests/hygiene.js`).
- Outside addresses, library versions, the font faces and their weights are config's, like the name, in the source, the scripts and the test fixtures; any other outside address waits in The outside review's list for its phase (`tests/hygiene.js`).
- Nothing a screen sets up outlives the render that drew it: charts, drag lists, intervals and the 3D body's one WebGL context (`tests/cleanup.js`).
- Storage keys keep "ironlog" whatever the app is called: they are built from `STORAGE_ID`, an identifier that never changes, since renaming it would leave saved logs behind. `tests/r49.js` holds the keys to their exact values.
- Moving code changes no behaviour: the suites and the coherence checks say so before a release is merged; the comparisons of whole builds stay pinned to the moves they proved, `tests/r36.js` (r35 and r52, the r36 split), `tests/r52.js` (r51 and r52, phase 3b, on wide histories, past midnight, with stale caches and on the demo) and `tests/r53w.js` (r52 and r53 the same way, each difference held to the r53 rule that makes it); and `tests/engine.js` runs the engine alone in Node against the page's answers, its lines run a ratchet above.
- The engine and the analytics read the log, the date and their caches only through the model they are given, all the way down: no clock, randomness, store, live model, page global or changing module value but the listed date formatters (`tests/hygiene.js`, rule 6). The code is read as written: `Date` only as `new Date(a date)`, `Date.UTC` or `Date.parse`, `Math` never as a value or `random`, no global read by a computed name, a formatter's `format` only called with a date written in place and never taken as a value, no module value written by name or by Object's own writers (`assign`, `defineProperty`, `defineProperties`, `setPrototypeOf`), and none made at load by running a function, whose closure could keep state. A value undefined only when it runs, a write through a local alias and a read built by reflection are beyond a reading of the code: `tests/engine.js` runs the engine with every module table frozen and the log watched for any attempt to change it, and review reads the rest. A function whose first parameter is `M` is read as one taking the model, and held to this rule with all it reaches.
